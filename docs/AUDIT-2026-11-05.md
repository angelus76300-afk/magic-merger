# Audit of Magic Merger, 5 November 2026 (roadmap 4.5.1)

> 6 November 2026, before the repository went public: rows A.V1, C.S-2, C.S-4, D.D33.5, E.H2b, E.S10-O1, risk 1 and section 1.10b were shortened. The steps of each weakness still open were taken out; the finding, its severity, where it lives and its fix stay. `docs/SETUP.md` section 7 lists what the owner changes.

Every claim in the docs, the pull requests and the game's own items was treated as unverified until found in the code and, where possible, seen to happen. The code is `main` at 46de1fc (#42). Nothing was deployed, nothing was written to the live database, no script called the Anthropic API or a live admin route, and no code was edited: this file and the frames in `docs/audit-2026-11-05/` are the only output.

**Who did what.** One session (this one) ran every check, the mutations, the library sample, the browser run, the live read only queries and the deployment history. Seven read only verifier subagents, each with a fresh context and a written brief (no edits, no wrangler, no network), read the code against one slice of the claims and wrote tables; their rows are marked by letter (A to F, plus the loop map). Every Critical and High row was either reproduced here (mutation, script, query or browser) or re-read here at the cited lines; where this session disagreed, the row was corrected and says so (for example D.D342.W1: a verifier said a test catches a broken fire ward; the mutation shows none does).

**Live reads** (all `wrangler d1 execute magic-merger --remote` with a SELECT; every answer reported `changed_db: false`): row counts, the 25 sample programs, cast counts, the spend ledger, daily challenges, open holds, design calls, open gaps, program histories of Light and Village, and counts of programs passing `data` or naming `process`. Plus `wrangler deployments list` and the session schedules, both read only.

**One disclosure.** To cast the 25 live programs, this session ran Claude-written code in Node, where nothing is sandboxed, in a container whose environment holds a Cloudflare token. That is the same exposure as finding O14. Before relying on it, the 25 programs and every live or trial program in the database were checked for `process`, `fetch`, `globalThis`, `constructor`, `import(` and `require(`: none names any of them.

**What works** (one line each): the money hold is atomic and tested; the $5 cap per invite has no bypass found; the burst guard holds under parallel requests; the daily challenge's secret pair leaks through no route; account switching keeps one account's save from the other; the hide switch of the Community tab is enforced on the server; the newcomer's path, every tab, reset, sign out and sign in work at 390 by 844; no secret is in the repository's history.

**What does not**, in order of harm (section 5 has the detail and the smallest fix):

1. **Critical**: unreviewed pull request code runs in CI with an account wide Cloudflare token, and the staging Worker that serves it holds the production admin token, which since 4.4.6 can be turned into a lasting owner passkey. The nightly Judge job also runs Claude-written code unsandboxed beside that token.
2. **Critical, latent**: the API designer's cron asks Opus again every 10 minutes whenever a design is refused or answered "none"; at about $0.10 a call that empties the month's $48 in about 3 days and stops the game for everyone.
3. **High**: deleting an account leaves the person's name on wonders shown on every island; export misses nine tables; a pending challenge win is posted by the next account on the device.
4. **High**: production is deployed by hand from session containers and branches; nothing gates a merge, nobody reviews, nothing rolls back.
5. **High**: checks that cannot fail (the fire ward, the staging guard, the CSP, every browser guard) and promises that are false (6 of 25 items; `w.body` drops `data`; a refusal shown as Village's description; honest challenge wins refused by an upper bound).

Severity raised by this session: rows A.V1, E.H1c and F.F7 (the verifiers rated them High) are one finding with O14 and E.S10-O1, risk 1, rated Critical here because the path from players' words to production credentials has no human gate before code runs.

### 1.10b What spell code can still reach (verifier C)


Spell code runs with `new Function("__g", '"use strict"; ...')` (runtime.ts:246). Nothing is shadowed, frozen or deleted: a grep for `Object.freeze`, `delete globalThis`, `lockdown` in frame.ts, checkframe.ts, checkworker.ts, runtime.ts and check.ts finds nothing. It sees the whole realm.

- In the check Worker (a classic worker from a blob): `self`, `globalThis`, `postMessage`, `addEventListener` and `onmessage` (it can see the next jobs, see C.S-4), `close()`. Also `importScripts` (script-src 'self': same-origin GETs, no credentials), and `new Worker(blob:)` (`worker-src blob:` allows nested workers). `fetch`, `XMLHttpRequest`, `WebSocket` and `EventSource` exist but are blocked by connect-src 'none', if the blob worker inherits the CSP (not verified in browsers). `indexedDB` and `caches` throw in an opaque origin. Then `navigator` (user agent, cores), `crypto`, `performance`, timers, `Function`, `eval` and `WebAssembly` (all allowed by 'unsafe-eval'), and the built-ins the check code relies on (`Math.random` is set by check.ts and can be replaced).
- In the World frame and the check frame fallback (sandboxed documents): `window`, `document` (it can draw any interface inside the iframe, such as a fake prompt), `location` (it can navigate itself to any URL), `history`, `Image` (img-src 'self' data: blob:), and `RTCPeerConnection`. It also reaches `parent.postMessage`, so every message the page accepts: save (replaces the island locally and on the account), cast, error (asks for a paid repair, at most 3 per program), chronicle (a paid Haiku call, once per 20 minutes), need, perf (only while the HUD is on), headroom, objective (a challenge win recorded on the server), island.
- Blocked by the sandbox flags: the page's DOM and storage, `localStorage`, `sessionStorage`, `document.cookie` (opaque origin), `window.open`, `alert`, navigating the top window, forms.
- Not reachable: the session token, the admin token and the invite link. They sit in the game page's localStorage and travel only as request headers from the page.

## 2. The library sample: 25 live items cast in Node

**How.** The 25 live programs were read from the live database with SELECT only (`spells` joined to `programs` where `status = 'live'`): the 10 with the most casts, Human, Serpent, Village, Ward (the ward) and Wormhole, and 10 drawn with `ORDER BY random()`. "Most cast" counts rows of `casts`, whose key is (player, program): it counts players per program, not casts, since the database keeps nothing else. Each program went through the real test run (`runCheck`, src/sim/check.ts) and then through an observation harness (scratchpad `library/cast.ts`): the same seeded check island (112 cells, seed 11, a dead villager and a wounded one by the target), cast against an identical island left alone, 30 s for a spell and 120 s for an artifact, counting per material, per creature kind and status, wards, landmarks, artifact deeds and bodies. No API call. Differences under about 30 cells are noise (a spell that draws random numbers shifts the island's own random stream), and healing of villagers cannot be read from hit points, because the island's villagers heal each other in the control too (traced: the wounded villager goes from 35 to 95 hp in both runs). Healing was therefore checked in the code.

**Result.** 24 of 25 pass their test run today. Against their own summary and intents: 12 match, 6 partly, 6 do something else, 1 could not be checked. The test run says whether something visible happened, not whether the item does what it says, so its pass rate tells nothing about promises.

## 5. The five biggest risks

**1. Unreviewed code runs with production credentials (Critical).**
preview.yml runs on every pull request from a branch of this repository, the feedback routine's included, as soon as it opens. It builds and uploads the PR's own code and configuration with `CLOUDFLARE_API_TOKEN`, which SETUP.md:132 gives Workers Scripts Edit and D1 Edit on the whole account, so a PR's code could reach production's resources, the live D1 included. The staging Worker that serves every preview holds `ADMIN_TOKEN` = MM_TOKEN, the production admin token (staging.yml). Since 4.4.6 that token can lead to a new owner passkey (E.S10-O1), and no route removes a passkey: a token that leaks once can become admin access that survives rotating it. The chain starts from players' words (the routine) or from any session that reads them (DAILY.md builders read the Ideas tab). Nothing shows it was used. Could not verify: whether the GitHub environment `preview` requires a reviewer (if it does, the first half is closed).
Smallest fix: run the preview only after the owner adds a label or approves the `preview` environment; give staging its own admin token; rotate ADMIN_TOKEN and MM_TOKEN; list the owner's passkeys and remove unknown ones. Size S, but the settings are the owner's (accounts, credentials).

**2. A cron loop that can spend the month and stop the game for everyone (Critical, latent).**
`designDue` (worker/evolve.ts:111-116) is true whenever no extension was stored in the last 20 h. A design answered "none" (the prompt offers it) or refused by `storeDesign` stores nothing, so the cron asks Opus again every 10 minutes: 144 calls a day, each held at $0.40 and costing about $0.10 (the three real ones: $0.094, $0.096, $0.110). At that rate `BUDGET_USD` ($48) is gone in about 3 days and every player's merges stop for the rest of the month. Not triggered yet: 3 design calls in November, all stored, and 320 spells with an open gap keep it due. The daily challenge has the same shape at a smaller scale (no row written when three tries land on existing items, so it retries every 10 minutes, worker/daily.ts:65-69). Related money gaps found by the verifiers: holds far below what a call can cost (a merge held at $0.004 can cost $0.083), wonder holds billed by the sweep after an hour while their batch still runs, batch holds that never release, `REWRITE_BUDGET_USD` checked on one rewrite path of three, `sweep` untested.
Smallest fix: record each design and daily attempt with its time, whatever the answer, and key `designDue` and `due()` on the attempt. Size S, with one test each.

**3. Players' data: what the account page promises is not what the code does (High).**
Deleting an account leaves the person's name in `wonders.by_name`, shown on every island as "found by <name>" (accounts.ts:583-607 never touches `wonders`), while the page promises "without your name" (src/account.ts:299). Export leaves out daily finds, the favorite, activity, perf, refusals, writes, rewrites and wonders. A pending challenge win and attempt live outside `PROGRESS_KEYS` (src/device-save.ts:20) and are posted by the next account that signs in on the device (src/challenges.ts:94-95). The staging copy keeps idea texts, vote reasons and account ids. Sessions copied the live database into their containers (3.9 MB and 4.8 MB) and wrote a test account flagged admin into production (#36).
Smallest fix: clear `wonders.by_name` on delete and add `wonders` to the deletion test; add the two challenge keys to `PROGRESS_KEYS`; strip `suggestions` text in the staging copy. Size S.

**4. Production is deployed by hand, from branches, with no gate, review or rollback (High).**
6 of the last 10 production deployments went out before their pull request merged (section 4), one of them with a migration applied to the live D1 from a branch before its PR existed. `main` is not protected, CI gates nothing (#32 merged with CI cancelled, #34 merged 7 s after opening), no PR was ever reviewed, no rollback was ever run, and the nightly Judge job runs 7 to 8 h late and has not run since part C. 4.5.2 plans to let sessions merge and deploy without the owner on top of this.
Smallest fix: a deploy workflow on push to `main` (migrations, deploy, smoke test at phone size, `wrangler rollback` and an issue on failure), and no Cloudflare token in session environments. Size M (4.5.2 item 1).

**5. Checks that cannot fail, and promises that are false (High).**
The ward against fire can be removed with all 242 checks green (section 3). The staging guard, the CSP, the iframes' sandbox and every browser guard (two tab island lock, watchdog, pending wins, account switch) have no test in CI. `fewestMerges` is an upper bound, so the guard against forged challenge wins refuses honest ones (reproduced: 5 merges claimed where 4 suffice, then a 400 and the win is dropped). The test run passes 24 of 25 sampled items while 6 of them do something other than their summary, and a frozen test run counts as a pass. `w.body()` drops `data`, which breaks up to 32 of 385 live programs; a refusal is shown as Village's description.
Smallest fix: the one line `data` fix in runtime.ts:1559 (repairs those programs without rewriting one); a fire spread check in npm test; a test:worker pass with `STAGING=1`; `fewestMerges` replaced by an exact search or the lower bound check removed; account-verify and verify-4.1 in CI. Size S each, M for the CI browser job.
